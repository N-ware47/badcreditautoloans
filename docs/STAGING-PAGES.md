This system targets only `https://staging2.badcreditautoloans.net` at
`/home/customer/www/staging2.badcreditautoloans.net/public_html`.
It never imports a database, plugins, uploads, WordPress options, or SEO metadata.
The existing automatic child-theme workflow remains separate and unchanged.

## Files and responsibilities

| File | Purpose |
| --- | --- |
| `content/pages-staging.json` | Explicit page keys, staging identity, content file, adoption baseline |
| `scripts/prepare-page.php` | Convert an export to staging URLs without editing its original |
| `scripts/export-page.php` | Export one local Gutenberg page; reads no SEO metadata |
| `scripts/validate-pages.php` | Offline manifest, URL, delimiter, attribute, and optional WordPress parser checks |
| `scripts/pages.php` | Register the `bc-pages` WP-CLI command |
| `scripts/lib/page-deployer.php` | Full-state checks, plans, locked updates, private backups and content rollback |
| `scripts/import-staging-home.php` | Read-only check using the original page-21 checksum; no apply path |
| `scripts/package-pages.py` | Allowlist only content and deployment scripts for private upload |
| `.github/workflows/deploy-staging-pages.yml` | Manual inspection, dry-run and approved apply |
| `tests/page-deployment-test.php` | Offline safety checks using a read-only database double |

The compatibility importer can no longer apply. Custom options belong to the new
registered WP-CLI command: `wp eval-file` passes positional arguments through
`$args`, so looking for `--apply` there was unreliable. Updates now use
`wp_slash()` to preserve backslashes in Gutenberg attributes.

## What deployment owns

Existing pages receive **post_content only**. Titles, slugs, publication state,
parents, templates, featured images, menus, and all page metadata stay under
dashboard control. The manifest `title` is used only when creating a new page.
New pages start as root-level drafts, attributed to an explicitly selected staging
editor. The SEO team reviews Rank Math and publishes drafts in WordPress.

No code imports `home-seo.json`. The package excludes SEO exports. Regular plugins
and themes are skipped during WP-CLI deployment, metadata API writes with the
`rank_math` prefix are blocked, and any metadata difference on an updated page
aborts the transaction. New pages also fail if a hook creates Rank Math metadata.
WordPress must-use plugins still load; review any hosting/custom MU save hooks
before the first apply. Database rollback cannot undo an external effect such as
an email sent by a hook.

Each page has an immutable manifest `key`. On first adoption, its explicit staging
ID, unique slug, and reviewed full-state hash must agree. There is no title match,
local-ID match, slug-only overwrite, or automatic adoption. After successful apply,
the private server ledger maps its key to its staging ID and last deployed hash.
A new page requires the slug to be absent, including drafts, trash and attachments.
Slug checks are deliberately strict across the installation; duplicate slugs or
renamed pages need a separate identity review.

The hash covers the entire post row and all page metadata, including Rank Math.
Even a dashboard SEO-only change can therefore block deployment. This is
conservative protection against overwriting a teammate's page. Active editor locks
also block deployment; close editors and wait at least three minutes before
inspection. Do not bypass a long-lived lock or change a baseline to clear an error.

## 2. First staging inspection (requires approval to upload/run)

Before first adoption, an existing page needs a verified staging ID, slug and
full-state baseline. The manifest originally used provisional page 21, slug `home`,
and `baseline_sha256: null`; the November 17 inspection verified that identity and
supplied the baseline recorded above. A new adoption must likewise stop until its
staging inspection succeeds. Do not use local homepage ID 6 as a staging ID.

After the user approves publishing these changes to GitHub and running the
inspection, run **Staging Gutenberg Pages (manual)** on `main` with operation
`inspect-home`. It uploads only the allowlisted deployment files to a private
`$HOME/bcal-page-releases/<run-id>-<attempt>/` directory, outside `public_html`.
It prints page 21's actual slug, title, status, full-state hash and content hash,
then tests the original `$HOME/staging-page-backups/home-baseline.sha256`.

Both commands must pass. If the legacy content checksum differs, stop and review
the server change with the page owner. Do not copy the printed new baseline into
the manifest just because inspection printed it before that failure. The old
checksum protects content only; titles/settings also need human review at adoption.

Update the manifest's slug to the inspected slug and its `baseline_sha256` to the
reviewed full-state hash. Keep `existing_id: 21` and `front_page: true`. Request
approval before pushing that update. Also retire/replace the old publicly located
importer after confirming its exact upload path; the new workflow uses only the
private copy and does not remove old uploads automatically.

For other existing pages, an authorized administrator can run the read-only command
below against a private release, then add the verified ID/slug/hash to the manifest:

```bash
wp --path=/home/customer/www/staging2.badcreditautoloans.net/public_html \
  --skip-plugins --skip-themes --require="$release/scripts/pages.php" \
  bc-pages inspect STAGING_PAGE_ID
```

Here and below, `$release` means the exact private release path from that workflow
run. Do not substitute a production path. Inspection does not require an editor ID.

## 3. Configure GitHub approvals before enabling apply

No GitHub settings were changed locally. Configure these in GitHub with approval:

1. Keep the existing `staging` environment for preview credentials. It needs
   `STAGING_SSH_HOST`, `STAGING_SSH_PORT`, `STAGING_SSH_USER`, the existing secret
   `STAGING_SSH_PRIVATE_KEY`, and variable `STAGING_PAGE_EDITOR_ID` set to a verified
   staging user ID with permission to edit the selected pages. The user must also
   be allowed to save the exported HTML without content filtering.
2. Create **`staging-pages-apply`**. Configure required reviewers, prevent self-review,
   restrict deployments to `main`, and disable administrator bypass where available.
   Provide the same staging SSH variables, editor ID and SSH secret in this environment.
3. Only after checking those protection rules, set the **environment-scoped** variable
   `STAGING_PAGES_APPLY_ENABLED=true` in `staging-pages-apply`. Do not define it at
   repository or organization scope. An auto-created environment has no enable flag
   and its apply job will fail.
4. Protect `main` and review changes to the manifest, workflows and deployment scripts.

Environment reviewer rules are GitHub settings, not rules a YAML file can install.
Their availability depends on repository visibility and plan. If required reviewers
are unavailable, leave the apply enable flag unset and use the manual reviewed
WP-CLI plan procedure below only after explicit approval.
See [GitHub's environment documentation](https://docs.github.com/en/actions/how-tos/deploy/configure-and-manage-deployments/manage-environments).

The SSH host key is pinned to the same value as the existing theme workflow. No
`ssh-keyscan`, insecure host checking, interactive passphrase handling or private-key
logging is used. Never paste private keys or passphrases into workflow inputs.

## 4. Preview, review and apply

1. After an approved push, manually dispatch operation `dry-run`, page `home` or a
   manifest key (`all` selects every manifest page).
2. Review the preview artifact and job summary: exact commit, page IDs/slugs,
   create/update actions, preserved title/status, content checksums, and plan hash.
   A successful dry-run changes no database rows, backups or ledger. It writes only
   a private plan file plus runner logs/artifacts.
3. Request approval for a separate operation `apply`. Type `APPLY STAGING PAGES` in
   its confirmation input. This run makes its **own fresh dry-run** before waiting
   at `staging-pages-apply`. Review that run's preview before approving the job.
4. Apply compares the approved plan and code/content hashes, then rechecks identities
   and full-state baselines inside a serializable InnoDB transaction. Post, metadata
   and relevant option rows/ranges remain locked until commit. An editor save that
   committed before those locks makes the plan stale and stops the import.
5. Before any page write, the importer saves an exclusive private backup. It verifies
   saved content, unchanged unrelated post fields and unchanged metadata before
   committing the selected pages together. It then publishes the new private ledger.

Both workflows share the existing `badcreditautoloans-staging` concurrency group.
An apply waiting for approval can delay theme deployment. GitHub concurrency allows
only one pending run in a group; avoid queuing multiple deployments during review.

No apply is possible through a content push alone. The new workflow has no push,
schedule, pull-request or workflow-run trigger. The old theme workflow still runs
on its original theme paths and uploads only the child theme.

## 5. Export another local page

With WP-CLI installed locally, run from PowerShell (replace `42` and `about`):

```powershell
wp --path=C:/wamp64/www/badcreditautoloans/wordpress --require=C:/badcreditautoloans/wordpress/scripts/export-page.php bc-export 42 about
```

This reads local page 42 and writes `content/pages/about.json` and
`content/pages/about-staging.json`. It does not change either WordPress database.
Add this entry to `content/pages-staging.json` for a genuinely new staging page:

```json
{
    "key": "about",
    "slug": "about",
    "file": "content/pages/about-staging.json",
    "title": "About",
    "existing_id": null,
    "baseline_sha256": null,
    "front_page": false
}
```

Do not change the key after deployment. Keep `existing_id: null` for pages created
by the system; their actual staging IDs live in the server ledger. If a page with
that slug already exists, inspect and explicitly adopt it instead. Publishing a new
draft, editing its SEO, title or settings changes its fingerprint; review and
reconcile those dashboard edits before deploying it again.

To prepare a different manual export:

```powershell
php scripts/prepare-page.php content/pages/about.json content/pages/about-staging.json
```

Only the configured local base URL and `{{theme_url}}` are replaced. Other localhost
URLs fail validation rather than being guessed. External links stay intact. Local
media IDs and reusable/navigation `ref` IDs are rejected because IDs differ across
databases. Remap those references separately; no uploads or plugins are transferred.
Images referenced by URL must already exist on staging. Unsupported custom blocks
stop the staging dry-run; review their registration before extending the system.

## 6. Verification after an approved apply

- Save the apply log's private backup path and deployed commit. The backup directory
  is `$HOME/staging-page-backups/bcal-pages/backups/` (0700); files are 0600.
- Run a new dry-run against the same content in a new plan path/release. It should
  report `unchanged` with matching full-state hashes. Do this before opening editors,
  because editor locks or dashboard changes intentionally invalidate the baseline.
- View the staging homepage/new draft preview, navigation, calculator, FAQ, mobile
  layout, images and links. Check for localhost URLs and unexpected 404s.
- Open the staging Gutenberg editor, check for invalid-block warnings, and let the
  SEO team verify Rank Math title, description, keywords, robots and schema in the
  dashboard. Deployment does not generate or import these fields.
- Do not visit or test production as part of this procedure.

## 7. A teammate changed a managed page

Stop, inspect, and compare the staging content/settings with the proposed export.
Merge or preserve the teammate's changes locally and obtain their agreement.
Changing `baseline_sha256` alone cannot override a managed page's server ledger.

For a specifically reviewed reconciliation, set `baseline_sha256` to the inspected
current hash **and** set optional `reconcile_from_sha256` to that key's previous
hash in the private `state.json`. This records both sides of the transition in a
reviewable manifest change. The dry-run shows `reconciled_from_sha256`. Obtain an
approved push and another reviewed apply. No script refreshes these values
automatically. Remove the historical reconciliation field after success; it cannot
authorize an unrelated future baseline mismatch.

## 8. Content rollback (always preview first; explicit apply approval required)

On staging SSH only, set the exact private release, backup and authorized editor ID
from the reviewed deployment. Example variables below are placeholders:

```bash
release="$HOME/bcal-page-releases/RUN-ATTEMPT"
backup="$HOME/staging-page-backups/bcal-pages/backups/TIMESTAMP-RANDOM.json"
editor_id=VERIFIED_STAGING_EDITOR_ID
wp_root=/home/customer/www/staging2.badcreditautoloans.net/public_html

wp --path="$wp_root" --skip-plugins --skip-themes --user="$editor_id" \
  --require="$release/scripts/pages.php" bc-pages rollback --page=home \
  --backup="$backup" --plan="$release/rollback-plan.json"
```

Review the output and its printed plan SHA-256. Only **after explicit approval**:

```bash
wp --path="$wp_root" --skip-plugins --skip-themes --user="$editor_id" \
  --require="$release/scripts/pages.php" bc-pages rollback --page=home \
  --backup="$backup" --plan="$release/rollback-plan.json" \
  --plan-sha256=REVIEWED_64_CHARACTER_HASH --apply
```

Rollback restores only the previous content, makes its own backup and advances
the ledger. It requires the page still to match both the selected backup's
after-hash and the current ledger. If anyone edited the page or metadata afterward,
rollback stops. Resolve that conflict manually with the page owner; never force a
stale backup into the database. Roll back individual existing pages by key.

A newly created page has no prior content. It remains a draft and is never deleted
automatically. After confirming nobody has edited it, an approved administrator
can trash it in WordPress. Retain its ledger entry as a record; reusing the same key
or resetting its identity requires a separate reviewed change.

## 9. Interrupted transaction or ledger failure

InnoDB failures before COMMIT roll back the selected page writes. Backups may remain
for audit. A crash after COMMIT but before ledger publication leaves a
`state-pending-*.json` journal, and further deployment/rollback plans stop.
The backup is completed with after-hashes and `state_after` before
COMMIT; the journal alone is not proof that COMMIT succeeded.

Do not delete the ledger or regenerate baselines. With explicit recovery approval,
use `bc-pages inspect ID` to compare every affected page with the saved before and
after hashes and compare the pending ledger with that backup's `state_after`.
If **all** affected pages match the saved after-hashes, an administrator can publish
that pending ledger atomically as `state.json`. If all match their before-hashes,
the transaction did not persist; retain the old ledger and archive the pending
journal outside the live state directory. Mixed or unexpected hashes require an
individual page review. Preserve the journal and backup until recovery is verified.

Do not run old release code after changing deployer versions; plan hashes include
the deployment code. Use the reviewed current release for both rollback preview
and apply. Private release and backup retention is manual so evidence is never
deleted automatically.
